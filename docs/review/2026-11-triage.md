### The five systemic causes

Most tickets trace back to one of these:

1. **There is no stable album identity.** Units, issues, decisions and URLs are keyed by folder path, and paths change constantly (moves, merges, artist merges, case differences).
2. **About 20 independent "same track / same album" matchers** disagree with each other: `ownership.lookup`, `missing._match`, `resolver.match_tracks`, `library.find_*_duplicates`, `issues.plan_album_copies`, `api._different_album`, `units.split_key`, `plexsync.album_share` and more.
3. **The writers don't coordinate.** The importer, the runner's apply, the HTTP trash and merge handlers, scans and the CLI all change the same folders with no lock and no shared "relocate" step. Path references go stale in six tables.
4. **Nothing checks Plex afterwards.** The app assumes a scan worked and that Plex grouped the files by their tags. It does neither reliably.
5. **`applied` means four things:** "fixed", "vanished", "key moved" and "superseded". Nothing distinguishes a fix that didn't stick.

## 2. Product rules: the contract

Some of these were decided before this review (see the dated sections of the README and earlier decisions). Others were decided on 2026-11-02, marked ★.

**Duplicates and editions**
- A duplicate is **the same MusicBrainz recording within the same release group**, whatever the pressing, edition or folder.
- ★ **Subset editions merge.** An edition all of whose recordings are on another edition of the same release group (standard vs Deluxe, CD vs vinyl vs remaster) merges into the **more complete edition's folder**. The best file of each track is kept (lossless, then hi-res, then bitrate) and the others go to Trash, which is restorable.
- ★ **Distinct editions stay separate and complete.** An edition with recordings of its own stays its own album. Example: the Doggystyle 2005 reissue, whose five "with intro" versions aren't on the 1993 original. For such an edition:
  - The edition goes **into the album tag**, e.g. `Doggystyle (2005 Reissue)`, so Plex shows separate albums.
  - **Every distinct edition is made complete** with its full tracklist. Shared songs are **copied** from the sibling edition's folder (and retagged) first, and downloaded only when no copy exists.
  - Copies of a shared recording across distinct editions are intended and are **not** duplicates.
- Different recordings are never duplicates: new remixes, live versions, demos, clean versus explicit.
- ★ An "explicit" disambiguation alone does **not** block a merge when both sides are the same recording ID. Clean and explicit versions are never merged with each other.
- Box sets stay whole. Their discs keep their own copies and are never merged out.
- ★ A track held only inside a box set **still counts as missing** for the standalone album.
- A song on a single, a compilation or another album (another release group) is **never** a duplicate and never a reason to skip a download.
- ★ Duplicate copies **inside one folder** are fixed automatically: same recording, lengths agree. Keep the best file and Trash the rest.
- When in doubt, don't pair. A missed duplicate is harmless; a false one deletes a file.

**Missing tracks**
- ★ **Nothing another edition holds is re-downloaded.**
  - For a **subset** edition, missing tracks are counted against what every edition folder of the release group holds.
  - For a **distinct** edition, they are counted against its own tracklist, and each gap is filled by **copying** from a sibling edition before any download.
  - Box sets don't count as holding (above).
- A release is flagged only when the library holds at least half of it, or the files came from an album download.
- *Download missing* is **never automatic**. Only the user starts it.
- ★ After a Download missing has fetched everything YouTube Music has, the leftovers go to a **"Tried — N not available"** bucket. That bucket sits **outside** the Needs-attention count and is never re-queued automatically. The user can retry or accept from there.

**Downloads and the library**
- ★ A download of an album that is already in the library goes **into that album's current folder**, whatever YouTube Music calls it.
- ★ The metadata manager does **not** move, merge or re-tag an album while a job for it is queued or downloading.
- Folder layout is `Artist/(Year) Album [Edition]/NN - Title`. The year is the original year.
- `/library` is a **case-insensitive** CIFS share: `SAM SMITH/` and `Sam Smith/` are the same folder. Reuse the on-disk spelling, and never assume a case-only rename creates a new folder.

**Plex**
- ★ **Files and tags are the source of truth.** After every change the app reads Plex back through the API and checks the invariant in §5, phase 4. If the invariant fails, it repairs Plex.
- ★ Plex section 5 has **"Prefer local metadata" = ON** and **Genres = Embedded Tags**, and the user wants it kept that way. Write everything that files can carry into the tags. Use the API only for what files can't carry (moods, posters, locks, matching) and for repairs. Read the prefs on every sync and warn when they change.
- ★ Splits are repaired with **Plex's album merge API first**, after testing it on one sandbox folder. Merges can't be undone, which is accepted. Tangled cases (albums spanning several folders) get forget-and-re-add, then a merge.
- Losing play history is acceptable.
- **Never** edit album or artist titles through the API, because that merges the item into any item with the same title. Never call `DELETE /library/metadata/{id}`.
- ★ Plex's server setting **"Allow media deletion" was switched OFF on 2026-11-02** at the user's request. Deletes go through the app's restorable Trash, and the app must never need Plex to delete media. **Unverified:** Plex may merge two albums that end up with the same match guid. Doggystyle album 262450 (7 tracks, `mbid://d7a96c61…`) is gone, and its tracks are now in 235578, which the app matched to the same MBID at 2026-11-01 20:52. The user was also tidying in Plex that morning, so it could have been a manual merge. The P1-C5 spike must test this. Until then, treat a match edit as a possible merge.

**Safety**
- Nothing is deleted. Trash is restorable and every change is journalled.
- Never act destructively on recording IDs that MusicBrainz disambiguates. The match may be a guess between pressings.
- Test in the sandbox (§8). A live data repair needs the user's go-ahead.

## 3. How the system fits together

```
 Browser (React)  <-- SSE /api/v1/events + polling (App 30s, Queue 4s, details 5s)
        |
 FastAPI  api.py (jobs, catalog, discover, /library/*)   metadata/routes.py (issues, albums, changes)
        |
 YouTube Music -> catalog.py (cache, pacing) -> discover.py (background scan)
        |
 worker.py: job -> tracks -> [gate: ownership.lookup over library_index] -> yt-dlp -> validate
            -> tagger (YouTube Music tags only) -> importer (path from YouTube Music tags, or jobs.target_dir)
            -> library_index.add_entry -> Plex partial scan 20 s later (per track) -> note_import after 60 s
        |
 metadata/runner.py, every 30 min / after imports settle (150 s) / full:
     library.scan -> plexsync.sync (plex_items mirror) -> dupes.sync -> units.sync_registry
     -> check_unit: resolver (MusicBrainz) -> desired -> issues.plan_unit -> missing.refresh
     apply loop: queue stage (Download missing -> worker.enqueue) -> file stage (tags, move, merge, trash)
               -> plex_catch_up (scan) -> Plex stage (genres, moods, match, poster, locks)
        |
 Plex  <- plex.py (HTTP)
```

**There are five representations of "the library", and nothing keeps them in step:**

| Store | Written by | Goes stale when |
|---|---|---|
| `library_index` (file scan) | `library.scan`, `importer` (`add_entry`, 8 columns, `dirpath` NULL), `apply.rekey_paths` | Artist merge deletes rows and never adds them back (`library.py:1667`). Case-mismatched import paths get pruned. A scan racing a move inserts phantom "unreadable" rows. |
| `md_albums` / `md_issues` (manager) | runner, apply, `units.sync_registry` | Any path change (keys are paths). Trash and artist-merge handlers never touch them. |
| `plex_items` (Plex mirror) | `plexsync.sync` | The full sync pages without a stable sort and deletes rows it didn't see (`plex.py:189-203`, `plexsync.py:140-146`). |
| `tracks` / `jobs` (downloads) | worker | `jobs.target_dir` is never rekeyed. `tracks.library_path` isn't updated by trash or artist merge. |
| `catalog_*` / `discover_*` | catalog, discover | Owned and Queued badges are not refreshed after an import (ArtistView). |

## 4. Root-cause analysis

### 4.A Actioned items clear, then come back

The lifecycle:
- `issues.save()` (`metadata/issues.py:157-221`) upserts by `key = f"{kind}:{ref}"`, where `ref` is usually the unit key, i.e. the folder path.
- When an existing row is re-planned it **becomes `open` again unless it is `dismissed` or `queued`** (`issues.py:183-188`). That includes rows that are `applied`.
- Rows that are no longer planned are closed as `applied` (`:204-221`).

The ways an issue comes back:

1. **A fix that doesn't stick re-opens silently.** After the apply, `_check_unit` re-plans (`runner.py:961`) and the upsert re-opens the issue, so with auto-apply on it loops.
   - DMX *(2010) Mixtape*: the MusicBrainz label "Siccness.net" is written by `do_tags`, then flagged as junk by `tagio.py:246-247`. That produced 23 tag batches.
   - Merges that leave files behind are re-detected (`issues.py:822-879`).
2. **Key changes.**
   - `rekey_unit` (`apply.py:151-171`) marks the old key's open issues `applied`. They disappear, then come back under the new key, where the **dismissed** state does not follow. 13 extra_tracks issues came back within minutes, e.g. Notorious B.I.G. *Duets*, Pearl Jam *Binaural*.
   - When the target key already exists, it **deletes the moving album's `md_albums` row** (`:154-156`), which loses `manual` (Accept match), `no_release` and `ignored`. 15 review_match issues came back. Example: Bliss n Eso *Circus in the Sky* was accepted 10-26 06:01, moved 06:02, and back in review at 06:22.
   - `units.split_folder` (`units.py:47-66`) changes keys whenever album tags in a folder diverge, and `sync_registry` deletes the old rows (`units.py:180-195`).
   - The trash and artist-merge handlers (`library.trash_paths`, `library.merge_artist_folders`) don't touch the metadata tables at all. 8 dismissed "Not identified" issues came back after artist merges.
3. **Download missing can't converge** (see 4.B). After queueing, the issue is set back to `open` (`missing.py:336-341`, `apply.py:275-293`, `runner.py:930-932`). Nothing records what was tried. The re-queue guard only looks at **active** jobs (`missing.py:314-318`). "Download missing all (N)" selects every open issue, including ones already tried (`AttentionSidebar.jsx:48-53`).
4. **Actions in the duplicates manager** (trash, "not duplicates", merge artists; `api.py:823-897`) don't update `md_issues`. Counts only change at the next full cycle, and the dup-analysis cache doesn't notice moves (`library.py:1827-1836`).
5. **UI.**
   - The sidebar counts include `queued` and `failed` (`views.py:151-160`).
   - The Review dialog removes rows optimistically, then reloads them as "queued" (`IssueList.jsx:278-283`, `:443-447`).
   - It doesn't listen to SSE.
   - No event is published after the file pass (`runner.py:973-979`).

### 4.B Download missing → Skipped "duplicate, different album"

The path:
1. **Detection.** `missing.compute` (`missing.py:56-100`) loads units with the **same `release_mbid` only** (`:50-53`). A track counts as held only when its file is matched to that release's release-track ID.
2. **Video choice.** `_match` (`:208-248`) picks the videos. Ranks 1 and 2 **ignore version markers**, and the album's held tracks aren't part of the assignment.
3. **Queueing.** `queue_download` queues `target_dir = main_unit` with a plain-list `track_filter`, and **no release or MBID mapping** goes with it (`:292-343`).
4. **The gate.** For every track, `worker.py:363-372` calls `find_duplicate` → `ownership.lookup` with the YouTube Music title and album. It is not given `target_dir` and has no MusicBrainz awareness: `ownership._COLUMNS` doesn't even load the `mb_*` columns.
   - On an **exact artist + title match on the "same album" it returns `have` even when the length or version disagrees** (`ownership.py:216-218`). The `mismatch` flag is ignored (`library_index.py:280-284`).
   - A skip writes **no `error_code` or message** (`worker.py:368-370`, `:627-629`).
5. **The Skipped list.** `api._different_album` (`api.py:276-279`) compares the raw folder name `(2019) Rare Ass Shit` with the album tag `Rare Ass Shit`. That flags 999 of the 1,008 skips, including all 558 that matched a file in the album's own target folder.

The 1,008 skips by cause:

| Cause | Skips | Who's wrong |
|---|---|---|
| The file is in **another edition folder of the same release group** (Slipknot *All Hope Is Gone* vs *[2018 Reissue]*; Wiz Khalifa *Rolling Papers* vs *(Deluxe Version)*) | 352 + 35 | The detector and the merge. Subset editions should have merged; distinct ones should copy from the sibling, not download. |
| Same folder, **length off by more than 5 s**, and the gate still said "have" | 158 | The gate |
| Same folder, a **small title spelling difference** the resolver rejects ("Come"/"Came", gap 2.7 s > 2.5 s at `resolver.py:142`) | 136 | The detector is too strict |
| Same folder, **a different track with the same title** (live disc 2 "Wake Up Dead" stood in for studio disc 1; clean vs explicit) | 72 | The gate |
| The video picker chose **a track already held** (Grinspoon "Black Friday (Live)" picked by position for studio "Black Friday") | 26 | The picker |
| The release lists **the same recording twice** | 18 | The detector |
| The detector was **stale** at queue time: `do_download_missing` computes right after the file-in step, and `skip_videos` compares rewritten `provider_track_id`s (`worker.py:319-322`) | 126 | Detector state |
| Matched a file **an earlier Download-missing job delivered** | 24 | Re-queue |
| A `[Single]` folder treated as the album (`library.py:85` strips every `[…]`) | 2 | Album identity |
| Matched file has since moved, so it can't be classified | 59 | – |

**Why the sibling edition folders survived the 2026-10-21 merges:**
- **Complementary editions never link.** `_sharing` (`issues.py:878-897`) only links copies that share a recording, so editions holding *different* parts of an album are never grouped.
- **Disambiguated recordings are dropped.** `plain_recordings` (`issues.py:798-811`) drops every recording that has a disambiguation. Every *Rolling Papers* track is marked "explicit".
- **Merges get undone.** That is problem D.

### 4.C Plex splits one album into several

The cause of each of the 472 split folders. Each folder takes the cause of its largest minority album.

| Cause | Folders |
|---|---|
| The app **moved files in** (album move, merge of copies, file-in), and Plex followed the item and **kept its old album** | 158 |
| Plex **re-created** items (the app renamed or moved them) and put them in a new album although the tags were final. Measured rate: 42% of re-created items | 115 |
| An album download was **scanned with YouTube Music tags**, then retagged; Plex never regroups | 82 |
| **Two files in one disc/track slot** (opus + m4a). These split 75% of the time | 30 |
| An older file was retagged in place after Plex's first scan | 26 |
| **Download missing** into an MusicBrainz-tagged folder, scanned with YouTube Music tags | 26 |
| The files still disagree on album, album artist or release MBID | 11 |
| A Plex untitled `''` album shared with other folders | 8 |
| Folders split exactly by disc (Death Cab *Plans*, Nas *God's Son*, …); these should still be one album | 4 |

**The timing behind it:**
1. `tagger.write_tags` writes YouTube Music tags only (`engine/tagger.py:33-60`).
2. The importer schedules a Plex scan 20 s after the track (`worker.py:438`, `importer.py:231-244`). Tracks finish about 35 s apart, so **an album download triggers one scan per track**.
3. The metadata manager's first tag write comes a median of 18–21 minutes later.
4. Download missing **already knows the release and the track mapping, then throws it away** (`missing.py:292-320`).

**Moves:**
- `do_album_copies` (`apply.py:704-762`), `_relocate` (`:380-439`) and `_file_in_downloads` (`:296-350`) move files without first retagging them to the destination's values.
- `plex_catch_up` then scans the destination first, *so that Plex follows the item* (`apply.py:924-929`). A followed item keeps its old album.

**Detection, which doesn't exist yet:**
- `plexsync.album_for_paths` takes the folder's **majority** album (`plexsync.py:357`), and `plan_unit` only acts on that one (`issues.py:445-519`). So minority albums never get genres, a match or locks.
- `plex.py` has no merge call.

**The "Not in Plex" fix:**
- It fires on absence from the mirror, and the mirror can be wrong because paging is unstable (`plex.py:189-203`). The fix hides the files, scans, **empties the whole section's trash** and restores them (`apply.py:833-893`).
- 9 of the 21 folders re-added this way are split now.

**Other Plex defects:**
- `wait_for_scan` returns True when no scan was ever seen (`plex.py:281-295`).
- `_verify_in_plex` only checks that the path exists (`worker.py:669-690`).

### 4.D Merge and layout move undo each other

1. `do_album_copies` moves the other copies' files into the keeper **without retagging them** and pins `release_mbid` on the keeper's key (`apply.py:744-753`).
2. On the next check, the moved-in files still carry the old album tag, so `units.split_folder` splits the folder into `folder|<old album>`. The pinned key vanishes, and the new unit resolves to the old release.
3. The layout move then sends those files back to the old folder.
4. On the next cycle, `plan_album_copies` sees two copies again and merges again.

**Evidence:**
- Laufey *Bewitched*:
  - 10-21 00:36: merged, 8 moved in, **27 worse copies trashed**.
  - 01:37: moved back.
  - 10-22 00:25: merged again, **27 trashed again**.
  - 00:37: moved back.
- Michael Jackson *Thriller 25*:
  - merges 10-21, 10-22 (twice) and **11-01 20:46**;
  - each followed by "Moved 4 files to … (1982) Thriller" about 5 minutes later.
- 117 or more Download-missing tracks were later trashed as "worse copies".
- Every move is another chance for Plex to split the album (4.C).

### 4.E Case study: Snoop Dogg *Doggystyle*, two editions mixed into one Plex album

The user reported this mid-review. It combines A, B and C, so it is the **pilot album** for phase 4 and the new phase 3b.

**What's on disk.** Both folders are in release group `649762c9`.

| Folder | Release | Tracks | Album / album-artist tags |
|---|---|---|---|
| `Snoop Dogg/(1993) Doggystyle` | `d7a96c61` (1993 original, with skits) | 18 + a loose `Snoop Doggy Dogg - Gz up, hoes down.opus` tagged **#18** | `Doggystyle` / `Snoop Dogg` |
| `Snoop Dogg/(1993) Doggystyle [2005 Reissue]` | `a2a412fb` (2005 reissue, skits folded into songs) | 13 | `Doggystyle` / `Snoop Dogg` (**identical**) |

**MusicBrainz** (cached `meta_cache` rows `mb:release:<id>`):
- **8 recordings are shared:** Bathtub, G Funk Intro, Gin and Juice, Murder Was the Case, Serial Killa, Who Am I, For All My Niggaz & Bitches, Ain't No Fun. Every one carries the disambiguation **`explicit`**.
- **5 are reissue-only "with intro, explicit" recordings:** Tha Shiznit, Lodi Dodi, Doggy Dogg World, Gz and Hustlas, Pump Pump.
- **The original has 10 recordings of its own:** the skits plus the plain versions of those 5.
- **By the rule in §2, both are distinct editions:** two complete albums, `Doggystyle` and `Doggystyle (2005 Reissue)`.

**What went wrong, in order:**
1. **2026-10-14 10:39.** The layout move filed `Doggystyle (Remastered)/` → `[2005 Reissue]` and its nested `Doggystyle (Remastered)/Doggystyle/` → `(1993) Doggystyle`.
   - Both got the **same album tag**; the edition went into the folder name only.
   - At 16:09 a `not_in_plex` re-add ran for both folders together, and Plex created **one album, 235578**, for both, because it groups by album and album-artist tags.
2. **The editions never merged or reconciled.** `plain_recordings` (`issues.py:798-811`) drops every disambiguated recording. All 8 shared ones say `explicit`, so `_sharing` found nothing in common and no `album_copies` issue was ever planned.
3. **Plex match flip-flop.** Both units resolve 235578 as "their" Plex album (`plexsync.album_for_paths` takes the folder's majority album, `plexsync.py:357`), and each check re-matches it to its own release:
   - 10-21 02:35 → original;
   - 10-22 22:39 → reissue;
   - 11-01 20:52 → original.
   - `plex_shared` didn't catch it. Each flip closes one unit's `unmatched` issue and opens the other's (bug A).
4. **Download missing, 10-21 07:06.** Counting per release (bug B), it **downloaded 7 songs the reissue folder already held** (same recording IDs) into `(1993) Doggystyle`. Plex put them in a **new album, 262450** (bug C).
5. **Still open:** "1 of 18 tracks missing", namely *Murder Was the Case*. YouTube Music doesn't have it, but the reissue folder holds **the same recording** (`38e75603`), so it could be copied. It will never resolve today.
6. **Kept extra collides.** The user dismissed "1 file not on Doggystyle" for `Gz up, hoes down` (a track cut from the release over samples), but it still carries **#18**. Plex shows two #18s.
7. **2026-11-02 08:12.** Plex showed one 28-track album with tracks 4–13 doubled. **The user deleted the three files that looked like duplicates:** original `01 - Bathtub.m4a` and `03 - Gin and Juice.m4a` (256 kbps), and reissue `02 - G Funk Intro.opus`.
   - The app's Trash has no record, because the delete went around the app.
   - `library_index` still lists them until the next scan.
   - Album 262450 is gone, and its other tracks are in 235578 (see the unverified note in §2).
   - "Allow media deletion" has since been switched off.

**What "fixed" looks like:**

- **Plex album `Doggystyle`** (1993, `mbid://d7a96c61`): exactly the 18 tracks of `(1993) Doggystyle`.
  - Bathtub and Gin and Juice are copied back from the reissue folder. They're opus 129, so offer a re-download of the 256 kbps version as an upgrade.
  - *Murder Was the Case* is copied in from the reissue folder as #8.
  - `Gz up, hoes down` is renumbered #19 (a bonus track after the release's last track).
- **Plex album `Doggystyle (2005 Reissue)`** (`mbid://a2a412fb`): exactly the 13 tracks of `[2005 Reissue]`, with the album tag `Doggystyle (2005 Reissue)`.
  - G Funk Intro is copied from the original's m4a.
- **No issue for either album flips back.** Neither album is re-matched again.

**The general classes this exposes, fixed in phase 3b below:**
- editions with identical album tags lumped by Plex;
- a Plex album claimed by two units (flip-flop);
- an "explicit" label blocking edition logic;
- a gap fillable from a sibling folder but sent to YouTube instead;
- a kept extra colliding on a track number;
- deletes made outside the app that it never notices;
- Plex's confusing view leading the user to delete real tracks.

### Phase 4: Plex prevent → detect → repair → verify (bug C)

**The invariant, for each album folder (disc subfolders folded in):**
1. Every file is exactly one Plex track, and Plex has no track there without a file.
2. All of the folder's tracks share **one** Plex album.
3. That album holds no tracks from other folders.
4. The album's title equals the album tag, and its artist equals the album-artist tag.
5. Its guid or `mbid://` agrees with the desired release or release group.
6. Track and disc numbers match.

Points 1–4 apply to **unidentified folders too**.

## 7. Checks to run after each phase (read-only SQL)

Run these against a `.backup` copy of `data/mdl.db`.

**Merge or move oscillation (target: 0 rows over 48 h):**
```sql
SELECT album_key, COUNT(*) FROM (SELECT batch_id, album_key FROM md_changes
  WHERE summary LIKE 'Merged %copies into%' AND applied_at > datetime('now','-2 days')
  GROUP BY batch_id) GROUP BY album_key HAVING COUNT(*) > 1;
```

**Download-missing skips (target: every skip has a reason, and none matched the same release group's recording in another edition):**
```sql
SELECT t.error_code, COUNT(*) FROM tracks t JOIN jobs j ON j.id = t.job_id
 WHERE j.target_dir IS NOT NULL AND t.status = 'skipped_duplicate'
   AND t.created_at > :deploy_time GROUP BY 1;
```

**Plex splits (target: falls to 0 after P1-R7, and stays at 0 for new imports):**
```sql
SELECT COUNT(*) FROM (SELECT folder FROM plex_items WHERE type = 'track'
  GROUP BY folder HAVING COUNT(DISTINCT parent_key) > 1);
```

**Issues that came back (target: 0 open issues re-opened from `applied` within 24 h):** this needs the P1-A1 state history, so add a `reopened_count` or an `md_issue_events` table.

## 8. How to test without disturbing the live app

The live `mdl-app` usually has a download queue running. Don't restart it to test.

- **Unit tests** in a throwaway container:
  ```
  docker run --rm --network none -e PYTHONDONTWRITEBYTECODE=1 -v "$PWD/backend:/src:ro" -w /src \
    --entrypoint /opt/engine-venv/bin/python music-downloader-mdl-app:latest -m unittest discover tests
  ```
- **Real-data checks:** do the same with `-v "$PWD/data:/live:ro"`. Take a sqlite `.backup` of `file:/live/mdl.db?mode=ro` into the container's `/tmp` and point `settings.data_dir` at it.
- **UI:** run a harness container with the API on 127.0.0.1:8001, plus vite and alpine-chrome (`--shm-size=1g`) on `--network container:<harness>`. Put scripts and screenshots in the gitignored `.cache/claude-sandbox/`.
- **Plex:** read-only GETs are fine. Anything that writes to Plex (merge, refresh, unlock, re-add) must be tried on one folder first, with the user's agreement.
- **One-off scripts:** set `logging.getLogger("httpx").setLevel(logging.WARNING)`, or the Plex token ends up in the logs.
- **Deploying:** `docker compose up -d --build` is the user's call unless they say otherwise.
